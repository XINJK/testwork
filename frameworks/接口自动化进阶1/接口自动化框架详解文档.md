# 接口自动化进阶框架详解文档

> 本文档基于项目 `接口自动化进阶1` 源码逐行分析，涵盖框架架构、每个包/每个py文件的作用与原理、用例执行流转全链路、分支走向，以及面试时如何讲解自己的优化与效益。

## 一、框架整体概述

### 1.1 技术栈

| 层级 | 技术 | 作用 |
|------|------|------|
| 测试框架 | pytest 9.1.1 | 用例组织、参数化、夹具、断言 |
| HTTP请求 | requests | 发送接口请求 |
| 数据驱动 | openpyxl | 读取Excel测试用例 |
| 变量渲染 | Jinja2 | 用例中动态变量（{{token}}）的模板替换 |
| JSON提取 | jsonpath | 从响应中按路径提取字段 |
| 数据库 | pymysql | MySQL查询与数据清理 |
| 验证码识别 | ddddocr + PIL + base64 | 图形验证码自动OCR识别 |
| 测试报告 | Allure | 可视化测试报告 |
| 日志 | pytest logging | 双路日志（文件+控制台） |

### 1.2 设计理念

本框架是一个**纯数据驱动的接口自动化框架**，核心理念是：

1. **测试数据与测试代码分离**：所有用例写在Excel中，Python代码只负责执行引擎，新增用例不需要改代码
2. **全局变量关联**：通过 `all` 字典 + Jinja2模板渲染，实现用例间的数据传递（如登录获取token后传给后续接口）
3. **断言策略可配置**：单字段断言、多字段断言、SQL断言自动识别分发，无需为不同用例写不同断言代码
4. **HTTP + JDBC 双断言**：不仅校验接口响应，还能直接查数据库校验数据落库正确性
5. **资源自动清理**：通过pytest fixture在全部用例执行完后自动清理测试产生的脏数据

## 三、根目录文件详解

### 3.1 run.py — 执行入口

```python
import os
import pytest

if __name__ == "__main__":
    pytest.main(["-vs", "./testcases/test_runner.py",
                 "--alluredir", "./report/json_report", "--clean-alluredir"])
    os.system("allure generate ./report/json_report -o ./report/html_report --lang zh --clean")
```

**作用与原理：**

- 这是整个框架的**唯一启动入口**，直接 `python run.py` 即可执行全部用例
- `pytest.main()` 以编程方式启动pytest，等价于命令行 `pytest -vs ./testcases/test_runner.py --alluredir ...`
- 参数解析：
  - `-v`：verbose，详细输出每个用例的执行结果
  - `-s`：关闭stdout捕获，允许print和logging输出到控制台
  - `--alluredir ./report/json_report`：指定allure原始结果输出目录
  - `--clean-alluredir`：执行前清空该目录，避免历史结果干扰
- `os.system("allure generate ...")`：pytest执行完毕后，调用allure命令行工具将JSON结果生成HTML报告
  - `--lang zh`：报告界面使用中文
  - `--clean`：覆盖已存在的HTML报告目录

**执行顺序：** pytest全部用例执行完成（无论成功失败）→ 才会执行allure generate → 最终生成可打开的HTML报告

### 3.2 conftest.py — 全局夹具与数据清理

```python
import pymysql
import pytest
from config.config import *
from utils.database import *

@pytest.fixture(scope="session", autouse=True)
def destroy_data():
    yield
    Database().execute_sqls(SQL1, SQL2, SQL3, SQL4)
```

**作用与原理：**

- conftest.py是pytest的**全局夹具配置文件**，pytest会自动发现并加载它，无需import
- `destroy_data` 是一个 `scope="session"` 的fixture，意味着：
  - **整个测试会话只执行一次**（不是每个用例、每个模块）
  - `autouse=True` 表示自动生效，不需要在用例函数参数中显式声明
- 执行时机：`yield` 之前的代码在**所有用例开始前**执行（这里没有前置代码），`yield` 之后的代码在**所有用例全部结束后**执行
- 清理逻辑：调用 `Database().execute_sqls(SQL1, SQL2, SQL3, SQL4)` 批量执行4条DELETE语句，清理测试过程中在 `base_data_store_center` 和 `op_logs` 表中产生的测试数据（cs_002、cs_003）
- 被注释掉的代码是原始的硬编码pymysql连接方式，已被 `Database` 类封装替代

**关键设计：数据清理放在session级而不是function级**，意味着5条用例共享同一份测试数据，用例4新增cs_002、用例5新增cs_003，全部跑完后一次性清理，避免每条用例都清理导致后续用例查不到数据。

**作用与原理：**

## 五、apiException包 — 自定义异常体系

### 5.1 diy_exception.py

```python
class DatabaseException(Exception):
    def __init__(self, message="数据库连接异常", code=-1):
        self.message = message
        self.code = code
        super().__init__(message, code)

class GetDataException(Exception):
    def __init__(self, message="数据库查询异常", code=-1):
        ...

class ExecuteSqlException(Exception):
    def __init__(self, message="数据库修改/删除异常", code=-1):
        ...
```

**作用与原理：**

- 定义了**3个自定义异常类**，都继承自Python内置的 `Exception`
- 每个异常携带 `message`（错误描述）和 `code`（错误码，默认-1）两个属性
- `super().__init__(message, code)` 调用父类Exception的初始化，确保异常能被正常raise和catch
- 三类异常对应数据库操作的三个阶段：

| 异常类 | 触发场景 | 在database.py中抛出位置 |
|--------|----------|------------------------|
| DatabaseException | 数据库连接失败 | `__get_connect()` 的except块 |
| GetDataException | 查询（SELECT）失败 | `get_one()` 的except块 |
| ExecuteSqlException | 增删改（INSERT/UPDATE/DELETE）失败 | `execute_sqls()` 的except块 |

**设计价值：** 区分异常类型后，上层可以精准catch特定异常做不同处理（如连接失败重试、查询失败记录日志），而不是全部笼统地抓Exception。

## 六、utils包 — 核心工具引擎（重点）

utils包是整个框架的**心脏**，包含11个模块，承担了从数据读取到请求发送、断言、提取的全部核心逻辑。

### 6.1 excel_utils.py — Excel数据读取

```python
import openpyxl
from config.config import EXCEL_FILE, SHEET_NAME

def read_excel():
    workbook = openpyxl.load_workbook(EXCEL_FILE)
    worksheet = workbook[SHEET_NAME]
    data = []
    keys = [cell.value for cell in worksheet[2]]
    for row in worksheet.iter_rows(min_row=3, values_only=True):
        dict_data = dict(zip(keys, row))
        if dict_data["is_true"]:
            data.append(dict_data)
    workbook.close()
    return data
```

**作用与原理：**

- 读取Excel中的测试用例，返回**字典列表**，每个字典代表一条用例
- Excel结构设计：
  - **第1行**：中文标题行（编号、模块、场景...），仅用于人工阅读，代码不读取
  - **第2行**：英文字段名行（id、feature、story...），代码作为字典的key
  - **第3行起**：实际用例数据
- `keys = [cell.value for cell in worksheet[2]]`：取出第2行所有单元格的值作为字段名列表
- `dict(zip(keys, row))`：将字段名列表与当前行数据值一一配对，组成字典
- `if dict_data["is_true"]`：**用例开关过滤**，只有 `is_true` 为True的用例才会被加入执行列表；为空或False的用例被跳过（如Excel第8行的空行is_true=None被过滤）
- 返回的 `data` 列表直接传给 `@pytest.mark.parametrize` 做参数化

**关键设计：is_true字段** 实现了用例的灵活启用/禁用，调试时只需把某行is_true改成False即可跳过该用例，不需要删除或注释代码。

### 6.2 case_analyse.py — 用例数据解析

```python
@allure.step("1.解析请求数据")
def case_analyse(case):
    method = case["method"]
    url = BASE_URL + case["path"]
    params = eval(case["params"]) if isinstance(case["params"], str) else None
    data = eval(case["data"]) if isinstance(case["data"], str) else None
    json = eval(case["json"]) if isinstance(case["json"], str) else None
    headers = eval(case["headers"]) if isinstance(case["headers"], str) else None
    files = eval(case["files"]) if isinstance(case["files"], str) else None

    request_data = {
        "method": method, "url": url, "params": params,
        "data": data, "json": json, "headers": headers, "files": files
    }
    logging.info(f"1.解析请求数据，请求数据为：{request_data}")
    allure.attach(f"{request_data}", name="解析数据结果")
    return request_data
```

**作用与原理：**

- 将Excel中读出的原始用例字典，**解析组装成requests库可直接使用的请求参数字典**
- `url = BASE_URL + case["path"]`：拼接完整请求地址（配置中的基础URL + Excel中的接口路径）
- 对params/data/json/headers/files五个字段统一处理：
  - `isinstance(case["params"], str)`：判断该字段是否为字符串类型
  - Excel中填了内容的字段读出来是字符串（如 `'{"pageIndex":1}'`），需要用 `eval()` 转成Python字典
  - Excel中没填的字段读出来是 `None`，直接赋值为 `None`，不执行eval（eval(None)会报错）
- `@allure.step("1.解析请求数据")`：将此函数标记为Allure报告中的一个步骤，报告中能看到"1.解析请求数据"这个步骤节点
- `allure.attach()`：将解析后的请求数据作为附件附加到Allure报告中，便于排查

**返回的request_data字典** 直接通过 `requests.request(**request_data)` 解包传入，key名与requests.request的参数名完全对应（method/url/params/data/json/headers/files）。

### 6.3 send_request.py — 请求发送

```python
@allure.step("2.发送HTTP请求")
def send_http_request(request_data):
    res = requests.request(**request_data)
    response = {
        "status_code": res.status_code,
        "json_data": res.json(),
        "response_time": res.elapsed.total_seconds() * 1000
    }
    logging.info(f"2.发送HTTP请求，响应文本为：{response}")
    return response

def send_jdbc_request(sql):
    return Database().get_one(sql)
```

**作用与原理：**

提供两个请求发送函数：

**send_http_request（HTTP请求）：**
- `requests.request(**request_data)`：使用requests库的通用request方法，通过 `**` 解包字典传入所有参数，支持GET/POST/PUT/DELETE等所有HTTP方法
- 不直接返回 `res` 对象，而是**重新组装成一个自定义字典**，包含三个关键字段：
  - `status_code`：HTTP状态码（如200、404、500）
  - `json_data`：响应体解析后的JSON字典（`res.json()`）
  - `response_time`：响应耗时，单位毫秒（`res.elapsed.total_seconds() * 1000`，elapsed默认是秒）
- 这样设计的好处是：后续断言和提取统一从这个字典取值，不需要记住requests Response对象的各种属性和方法

**send_jdbc_request（JDBC/数据库请求）：**
- 封装了数据库查询，调用 `Database().get_one(sql)` 执行SQL并返回一行结果（字典形式，因为用了DictCursor）
- 被 `asserts.py` 的数据库断言和 `extractor.py` 的SQL提取共同调用

### 6.4 get_keywords.py — JSONPath提取工具

```python
class GetKeywords:
    @staticmethod
    def get_keyword(data, name, index=0):
        try:
            result = jsonpath.jsonpath(data, f"$..{name}")[index]
        except Exception as e:
            result = False
        if result is False:
            logging.error(f"jsonpath提取失败...")
        else:
            return result

    @staticmethod
    def get_keywords(data, name):
        try:
            result = jsonpath.jsonpath(data, f"$..{name}")
        except Exception as e:
            result = False
        ...
        return result
```

**作用与原理：**

- 基于 `jsonpath` 库，从嵌套的JSON响应中**按字段名递归提取值**
- `$..{name}` 是JSONPath语法，`$` 表示根节点，`..` 表示递归下降（在所有层级中查找），`{name}` 是要找的字段名
- 例如响应为 `{"code":200,"data":{"token":"abc"}}`，`$..token` 会找到 `["abc"]`

**两个方法的区别：**

| 方法 | 返回值 | 适用场景 |
|------|--------|----------|
| `get_keyword(data, name, index=0)` | 单个值（列表中第index个） | 字段唯一，取第一个匹配值 |
| `get_keywords(data, name)` | 整个列表（所有匹配值） | 字段在响应中出现多次，需要全部校验 |

- `get_keyword` 默认 `index=0`，取第一个匹配项；在 `base_assert.py` 的type断言中，当 `index="all"` 时会调用 `get_keywords` 取全部
- 异常处理：jsonpath找不到字段时返回 `False`（不是抛异常），代码中统一判断 `result is False` 后记录错误日志
- 都用 `@staticmethod` 装饰，不需要实例化，直接 `GetKeywords.get_keyword(...)` 调用

### 6.5 asserts.py — 断言调度器（策略模式核心）

这是框架中**设计模式最集中、最能体现架构能力**的模块。

#### 6.5.1 HTTP断言体系

```python
class DataAssert(ABC):
    @abstractmethod
    def http_assert(self, case, res):
        pass

class SingleAssert(DataAssert):
    @allure.step("3.HTTP响应断言")
    def http_assert(self, case, res):
        if case["check"]:
            result = GetKeywords.get_keyword(res, case["check"])
            assert result == case["expected"]
        else:
            assert case["expected"] in str(res)

class MultipleAssert(DataAssert):
    @allure.step("3.HTTP多重响应断言")
    def http_assert(self, case, res):
        if case["check"]:
            MainAssert(case, res).main_assert()
```

**策略模式解析：**
- `DataAssert(ABC)` 是抽象基类，定义了 `http_assert` 抽象方法，所有断言策略必须实现它
- `SingleAssert`：单字段断言策略。当check字段是单个字段名（如 `"code"`）时使用
  - 有check值：用JSONPath提取该字段的实际值，与expected做 `==` 精确断言
  - 无check值：将expected作为字符串，判断是否 `in` 响应文本中（模糊包含断言）
- `MultipleAssert`：多字段断言策略。当check字段是字典字符串（如 `'{"status_code":200,"code":200}'`）时使用，委托给 `MainAssert` 处理

#### 6.5.2 断言分发器（核心）

```python
def obj_processor(case):
    try:
        eval(case["check"])
    except:
        return SingleAssert()
    else:
        return MultipleAssert()

def http_assert(case, res):
    obj_processor(case).http_assert(case, res)
```

**分发原理（用eval的成功/失败来判断用例类型）：**
- `eval(case["check"])` 尝试将check字段当作Python表达式执行
- 如果check是 `"code"`：`eval("code")` 会尝试找名为code的变量，找不到 → 抛NameError → 进入except → 返回 `SingleAssert()`
- 如果check是 `'{"status_code":200,...}'`：`eval()` 成功返回字典 → 进入else → 返回 `MultipleAssert()`
- 这是一种**巧妙的类型探测机制**，不需要额外的标记字段，用check内容本身的语法特征自动区分单/多断言

#### 6.5.3 数据库断言体系

```python
class DatabaseAssert(ABC):
    @abstractmethod
    def jdbc_assert(self, case):
        pass

class SingleDatabaseAssert(DatabaseAssert):
    def jdbc_assert(self, case):
        if case["sql_check"] and case["sql_expected"]:
            result = send_jdbc_request(case["sql_check"])
            assert case["sql_expected"] in str(result)

class MultipleDatabaseAssert(DatabaseAssert):
    def jdbc_assert(self, case):
        if case["sql_check"] and case["sql_expected"]:
            sql_check = eval(case["sql_check"])
            sql_expected = eval(case["sql_expected"])
            for sql, expected in zip(sql_check, sql_expected):
                result = send_jdbc_request(sql)
                pytest.assume(expected in str(result))

def sql_processor(case):
    try:
        eval(case["sql_check"]) and eval(case["sql_expected"])
    except:
        return SingleDatabaseAssert()
    else:
        return MultipleDatabaseAssert()
```

**数据库断言与HTTP断言同构，也是策略模式：**
- `SingleDatabaseAssert`：单条SQL断言。sql_check是普通SQL字符串（如 `'select ... where code="cs_003"'`），eval会失败（SQL不是合法Python表达式）→ 走单断言
- `MultipleDatabaseAssert`：多条SQL断言。sql_check是元组字符串（如 `'("select...", "SELECT...")'`），eval成功返回元组 → 走多断言，用 `zip` 将SQL列表和预期值列表一一配对，逐条查询断言
- 多SQL断言使用 `pytest.assume()`（软断言）：一条失败不会中断，继续执行后续SQL断言，最终统一报告所有失败项
- 单SQL断言使用 `assert`（硬断言）：失败立即中断

### 6.6 base_assert.py — 基础断言方法库

```python
class BaseAssert:
    @staticmethod
    def status_code_assert(result, status_code): ...
    @staticmethod
    def code_assert(result, code): ...
    @staticmethod
    def str_assert(check_name, result): ...
    @staticmethod
    def type_assert(check_name, expected_type): ...
    @staticmethod
    def time_assert(response_time, expected_time): ...

class MainAssert(BaseAssert):
    def __init__(self, case, result):
        self.__case = case
        self.__result = result

    def main_assert(self):
        for key, value in eval(self.__case["check"]).items():
            if key == "status_code":
                pytest.assume(self.status_code_assert(self.__result, value))
            if key == "code":
                pytest.assume(self.code_assert(self.__result, value))
            if key == "str":
                for v in value:
                    pytest.assume(self.str_assert(v, self.__result))
            if key == "type":
                for v in value:
                    check_name = v.get("check_name")
                    expected_type = v.get("expected_type")
                    index = v.get("index")
                    if index == "all":
                        res_list = GetKeywords.get_keywords(self.__result, check_name)
                        for res in res_list:
                            pytest.assume(self.type_assert(res, expected_type))
                    if isinstance(index, int):
                        res = GetKeywords.get_keyword(self.__result, check_name, index)
                        pytest.assume(self.type_assert(res, expected_type))
            if key == "time":
                response_time = GetKeywords.get_keyword(self.__result, "response_time")
                pytest.assume(self.time_assert(response_time, value))
```

**作用与原理：**

- `BaseAssert` 提供5种**原子断言方法**，都是静态方法：

| 方法 | 校验内容 | 示例 |
|------|----------|------|
| status_code_assert | HTTP状态码 | 预期200 |
| code_assert | 响应体中的业务code字段 | 预期200 |
| str_assert | 字符串包含 | 预期"success"在响应中 |
| type_assert | 字段数据类型 | 预期code是int类型 |
| time_assert | 响应时间 | 预期≤100ms |

- `MainAssert` 继承 `BaseAssert`，是**多字段断言的调度器**：
  - 遍历check字典中的每个key，根据key名分发到对应的原子断言方法
  - 全部使用 `pytest.assume()` 软断言，一个字段失败不影响其他字段继续校验
  - `self.__case` 和 `self.__result` 用双下划线前缀私有化，体现封装思想

**type断言的index设计（最精巧）：**
- `index` 可以是整数（如 `0`）或字符串 `"all"`
- `index=0`：调用 `get_keyword` 取第一个匹配项，校验它的类型
- `index="all"`：调用 `get_keywords` 取所有匹配项的列表，遍历每个元素校验类型
- 这解决了JSON中同名字段出现多次时（如列表中每个元素都有pageSize），是只校验第一个还是全部校验的问题

### 6.8 database.py — 数据库操作封装

```python
class Database:
    def __init__(self):
        self.__db = self.__get_connect()

    @staticmethod
    def __get_connect():
        try:
            conn = pymysql.Connect(
                host=DB_HOST, port=DB_PORT, database=DB_NAME,
                user=DB_USER, password=DB_PASSWORD,
                charset="utf8", autocommit=True
            )
            return conn
        except Exception as e:
            logging.error(f"数据库连接失败，错误异常是{e}")
            raise DatabaseException()

    def get_one(self, sql):
        try:
            if self.__db:
                with self.__db.cursor(DictCursor) as cur:
                    cur.execute(sql)
                    return cur.fetchone()
        except Exception as e:
            logging.error(f"数据库查询失败，错误异常是{e}")
            raise GetDataException()

    def execute_sqls(self, *sqls):
        try:
            if self.__db:
                with self.__db.cursor(DictCursor) as cur:
                    for sql in sqls:
                        cur.execute(sql)
        except Exception as e:
            logging.error(f"数据库修改/删除失败，错误异常是{e}")
            raise ExecuteSqlException()
```

**作用与原理：**

- 封装了pymysql的数据库操作，对外提供3个方法，内部处理连接、异常、资源释放

**三个公开方法：**

| 方法 | 功能 | 返回值 | 使用场景 |
|------|------|--------|----------|
| `get_one(sql)` | 执行SELECT查询 | 一行结果（字典） | 数据库断言、SQL提取 |
| `execute_sqls(*sqls)` | 批量执行增删改 | 无 | conftest数据清理 |
| `__init__` | 实例化时自动建立连接 | - | - |

**关键设计细节：**
1. `__get_connect()` 用 `@staticmethod` + 双下划线私有化，只在内部调用
2. `autocommit=True`：自动提交，DML语句（INSERT/UPDATE/DELETE）执行后立即生效，不需要手动conn.commit()
3. `DictCursor`：游标使用字典游标，查询结果以 `{字段名: 值}` 字典形式返回，而不是默认的元组，方便按字段名取值
4. `with self.__db.cursor(DictCursor) as cur`：使用with上下文管理器，游标使用完自动关闭，不需要手动cur.close()
5. `*sqls` 可变参数：`execute_sqls(SQL1, SQL2, SQL3, SQL4)` 可以传任意多条SQL，内部遍历执行
6. 每个方法都有try-except，捕获异常后记录日志并**抛出对应的自定义异常**（DatabaseException/GetDataException/ExecuteSqlException），而不是把pymysql的原始异常直接暴露给上层

### 6.9 data_preprocessor.py — 数据预处理（验证码OCR）

```python
import base64
import ddddocr
from PIL import Image
from io import BytesIO

def dddd_ocr_text(data):
    encode_data = data.split(",")[1]
    decode_data = base64.b64decode(encode_data)
    image = Image.open(BytesIO(decode_data))
    image_bytes = BytesIO()
    image.save(image_bytes, format="PNG")
    image_bytes = image_bytes.getvalue()
    ocr = ddddocr.DdddOcr()
    text = ocr.classification(image_bytes)
    return text
```

**作用与原理：**

- 处理**图形验证码的自动识别**，是登录场景的关键前置步骤
- 输入是验证码接口返回的base64编码图片字符串（格式如 `data:image/jpeg;base64,/9j/4AAQ...`）
- 处理流程（6步）：

```
base64字符串 → 去头(逗号分割取第2段) → base64解码 → 
PIL打开为图像对象 → 转存为PNG格式字节流 → ddddocr神经网络识别 → 验证码文本
```

**每步详解：**
1. `data.split(",")[1]`：base64数据URL格式为 `data:image/jpeg;base64,编码内容`，用逗号分割后取第2段（索引1），即纯base64编码
2. `base64.b64decode(encode_data)`：将base64字符串解码为原始二进制字节数据
3. `Image.open(BytesIO(decode_data))`：PIL不能直接从字节打开，需要用BytesIO包装成"类文件对象"再打开
4. `image.save(image_bytes, format="PNG")`：将图片统一转存为PNG格式的字节流（ddddocr对PNG支持最好）
5. `image_bytes.getvalue()`：从BytesIO缓冲区取出全部字节数据
6. `ddddocr.DdddOcr().classification(image_bytes)`：初始化ddddocr（带深度学习模型），对图片字节进行分类识别，返回识别出的字符串

**在框架中的调用方式：** 用例2的data字段中写了 `captcha: dddd_ocr_text("{{image}}")`，在test_runner.py中通过 `eval()` 执行这个函数调用，自动识别验证码后填入登录请求。

**逐行深度解析：**

#### 第17行：`data = read_excel()`
- **类属性**，在类定义时就执行，读取Excel全部用例数据
- 只执行一次，所有用例共享这份数据
- 此时data是一个字典列表，如 `[{用例1}, {用例2}, {用例3}, {用例4}, {用例5}]`

#### 第19行：`all = {}`
- **类属性**，全局变量字典，初始为空
- 用于存储用例间需要传递的动态数据（token、sn、image等）
- 所有用例共享这同一个字典，前一条用例提取的数据后一条可以直接用

#### 第21行：`@pytest.mark.parametrize("case", data)`
- pytest参数化装饰器，将data列表中的每个元素（每条用例字典）依次传给 `test_case` 方法

#### 第29行：`allure_init(case)`
- 初始化Allure报告的动态标题、模块、场景

#### 第30行：`logging.info(...)`
- 记录用例开始执行的日志，包含ID、模块、场景、标题

#### 第32行：`request_data = case_analyse(case)`
- **步骤1**：解析用例数据，组装成requests可用的请求参数字典

#### 第33行：`res = send_http_request(request_data)`
- **步骤2**：发送HTTP请求，返回包含status_code/json_data/response_time的响应字典

#### 第36行：`http_assert(case, res)`
- **步骤3**：HTTP响应断言，自动判断单/多断言策略并执行

#### 第44行：`jdbc_assert(case)`
- **步骤4**：数据库断言，自动判断单/多SQL断言策略并执行

#### 第47行：`json_extractor(case, all, res)`
- **步骤5**：从HTTP响应中提取数据存入全局变量all

#### 第49行：`jdbc_extractor(case, all)`
- **步骤6**：从数据库中提取数据存入全局变量all

```
  │     │     └─ 类加载时执行 data = read_excel() → 读取Excel，过滤is_true，得到5条用例
  │     │     └─ 类加载时执行 all = {} → 初始化全局变量字典
  │     ├─ @pytest.mark.parametrize("case", data) → 将5条用例展开为5个测试节点
  │     └─ session级fixture destroy_data 前置部分执行（无代码，直接yield）
  │
  └─ 开始逐条执行用例
```

### 9.2 单条用例执行的8个步骤

以**用例2（登录）**为例，完整流转如下：

```
用例2开始执行
  │
  ├─【步骤0】Jinja2模板渲染 + eval
  │   all = self.all  (此时all中已有上一条用例提取的 {"sn":"xxx", "image":"base64..."} )
  │   str(case) → 字符串中包含 {{sn}} 和 {{image}} 占位符
  │   Template(...).render(all) → {{sn}}替换为实际sn值，{{image}}替换为base64图片数据
  │   eval(...) → 字符串转字典，同时执行 dddd_ocr_text("base64图片") → 识别出验证码字符串
  │   结果：case字典中的data字段现在包含真实的sn和识别出的captcha
  │
  ├─【步骤1】allure_init(case)
  │   设置报告：feature=登录, story=登录, title="ID:2--正常登录获取token"
  │
  ├─【步骤2】case_analyse(case) → 解析请求数据
  │   method=post, url=BASE_URL+/api/auth/login
  │   headers=eval后字典, data=eval后字典(含真实sn和captcha)
  │   其余params/json/files为None
  │   返回request_data字典
  │
  ├─【步骤3】send_http_request(request_data) → 发送请求
  │   requests.request(**request_data) → POST请求发送到登录接口
  │   组装response = {status_code:200, json_data:{code:200,token:"abc"}, response_time:45.2}
  │
  ├─【步骤4】http_assert(case, res) → HTTP断言
  │   obj_processor(case):
  │     eval("code") → NameError → 返回 SingleAssert()
  │   SingleAssert.http_assert:
  │     case["check"]="code" 非空 → GetKeywords.get_keyword(res, "code") → 200
  │     assert 200 == case["expected"](200) → 通过
  │
  ├─【步骤5】jdbc_assert(case) → 数据库断言
  │   sql_processor(case):
  │     case["sql_check"]=None → if条件不满足 → 直接跳过，不执行任何数据库查询
  │
  ├─【步骤6】json_extractor(case, all, res) → JSON提取
  │   case["jsonExData"]='{"token":"token"}' 非空
  │   eval → {"token":"token"}
  │   遍历: key="token", value="token"
  │     GetKeywords.get_keyword(res, "token") → "abc" (从响应中提取token字段)
  │     all["token"] = "abc"
  │   此时all = {"sn":"xxx", "image":"...", "token":"abc"}
  │
  ├─【步骤7】jdbc_extractor(case, all) → SQL提取
  │   case["sqlExData"]=None → 跳过
  │
  └─ 用例2执行完成，all字典中新增了token，供后续用例3/4/5使用
```

### 9.4 全局变量all的生命周期

```
用例执行前: all = {}
    │
用例1执行: json_extractor提取sn和image
    │       all = {"sn": "xxx", "image": "base64..."}
    │
用例2执行: 渲染时使用all中的sn和image
    │       eval执行dddd_ocr_text(image)识别验证码
    │       json_extractor提取token
    │       all = {"sn": "xxx", "image": "...", "token": "abc"}
    │
用例3执行: 渲染时使用all中的token填入headers的x-auth-token
    │       无提取，all不变
    │
用例4执行: 渲染时使用token
    │       无提取，all不变
    │
用例5执行: 渲染时使用token
    │       无提取，all不变
    │
全部用例结束: conftest的destroy_data fixture执行后置清理
            all字典随TestRunner类生命周期结束而销毁
```

**关键理解：all字典是"累积式"的**，前面用例提取的变量不会被清除，后续所有用例都能引用。这实现了典型的接口测试场景：登录获取token → 后续所有需要鉴权的接口引用token。

### 9.5 异常分支与失败处理

**断言失败的流转：**
- 单断言（SingleAssert/SingleDatabaseAssert）使用 `assert`：失败立即抛出AssertionError，当前用例标记为FAILED，后续步骤（提取等）**不再执行**
- 多断言（MultipleAssert/MultipleDatabaseAssert）使用 `pytest.assume`：失败记录但不中断，继续执行后续断言，全部执行完后统一报告失败项
- 注意：即使HTTP断言失败，只要用的是assume软断言，后续的jdbc_assert、extractor仍会继续执行

**用例间依赖失败的传导：**
- 如果用例1（验证码）失败，sn和image没有被提取到all中
- 用例2渲染时 {{sn}} 和 {{image}} 会被替换为空字符串（Jinja2对未定义变量默认渲染为空）
- 用例2的登录请求会因为缺少正确的sn和验证码而失败
- token提取不到 → 用例3/4/5的headers中token为空 → 全部鉴权失败
- 这是数据驱动框架的典型特征：**前置用例失败会导致后续依赖用例连锁失败**

**数据库异常的流转：**
- 数据库连接失败 → DatabaseException被raise → 如果在用例执行中（jdbc_assert/jdbc_extractor），会导致用例ERROR
- 如果在conftest的destroy_data中（全部用例结束后），异常会在fixture teardown阶段抛出，不影响用例结果但会在日志中记录

## 十、框架设计模式与核心原理总结

### 10.1 使用的设计模式

| 设计模式 | 应用位置 | 体现 |
|----------|----------|------|
| **策略模式** | asserts.py | DataAssert抽象基类 + SingleAssert/MultipleAssert具体策略 + obj_processor分发器 |
| **模板方法模式** | test_runner.py | test_case方法定义了固定的8步执行骨架，具体实现由各utils模块提供 |
| **数据驱动模式** | excel_utils + parametrize | 测试数据与代码分离，Excel中新增用例不需要改代码 |
| **单例思想** | TestRunner.all | 类属性all被所有用例实例共享，实现全局状态 |
| **外观模式** | send_request.py | send_http_request封装了requests的复杂细节，对外只暴露一个简单函数 |
| **工厂模式思想** | obj_processor/sql_processor | 根据输入特征动态创建并返回对应的断言策略对象 |

### 10.2 核心技术亮点

1. **Jinja2 + eval 双层动态渲染**：先模板替换变量，再eval转回字典（同时执行嵌入的函数调用如OCR），实现了用例数据的完全动态化
2. **eval探测式策略分发**：用 `eval(check)` 是否抛异常来自动判断单/多断言，不需要额外标记字段
3. **HTTP + JDBC 双断言通道**：接口响应和数据库落库双重校验，确保数据正确性
4. **JSONPath递归提取**：`$..field` 语法在任意嵌套层级中查找字段，不需要写完整路径
5. **软断言pytest.assume**：多字段断言时一个失败不影响其他，一次执行暴露全部问题
6. **验证码自动OCR**：ddddocr集成，登录场景全自动，无需人工介入
7. **session级数据清理**：全部用例跑完后自动清理测试数据，保持环境干净

## 十一、面试话术：我在框架中做的优化与效益

> 以下话术结合本框架的实际代码，按照"问题背景 → 我做了什么 → 技术原理 → 带来的效益"的结构组织，面试时可以直接使用。

### 11.1 优化点1：断言体系从硬编码到策略模式重构

**面试话术：**

"在框架早期版本中，断言逻辑是写死在test_case方法里的if-else——如果check是单字段就走一套逻辑，如果是多字段就走另一套，后来加了SQL断言后代码越来越臃肿，新增一种断言类型就要改主流程代码，违反开闭原则。

我做的优化是**引入策略模式重构断言体系**：定义了DataAssert抽象基类，抽出http_assert接口方法；然后实现SingleAssert和MultipleAssert两个具体策略类，分别封装单字段断言和多字段断言的算法；再写一个obj_processor工厂函数，通过eval(check)是否抛异常来自动判断用例类型并返回对应策略对象。数据库断言也用同样的模式做了SingleDatabaseAssert和MultipleDatabaseAssert。

这样做的效益是：第一，test_case主流程里只需要一行 `http_assert(case, res)`，完全不需要知道内部走的是单断言还是多断言，主流程代码从几十行缩减到一行；第二，后续新增断言类型（比如正则断言、XML断言）只需要新增一个策略类，不需要改任何已有代码，符合开闭原则；第三，单断言用硬assert快速失败，多断言用pytest.assume软断言一次暴露全部问题，两种策略各自最优。"

### 11.2 优化点2：全局变量关联机制（Jinja2模板渲染）

**面试话术：**

"接口测试中最常见的痛点是**用例间的数据依赖**——登录接口返回的token要传给后面所有需要鉴权的接口，订单号要传给支付接口。早期方案是在每个用例里硬编码写死token，或者用全局变量一个个手动赋值，换个环境token变了就要改好多地方，而且用例顺序一变就全乱了。

我设计的方案是**Jinja2模板引擎 + 全局变量字典的关联机制**：在TestRunner类上维护一个all字典作为全局变量存储，每条用例执行完后通过extractor把需要传递的数据（token、user_id等）提取并存入all；下一条用例执行时，先用 `Template(str(case)).render(all)` 把用例字符串中的 `{{token}}` 占位符替换成all中的真实值，再eval转回字典。

这个设计的效益：第一，用例数据完全声明式，Excel里写 `{{token}}` 就行，不需要写任何Python代码，测试人员不需要懂编程也能维护用例；第二，变量来源透明，all字典里有什么就能用什么，提取和使用分离，符合单一职责；第三，支持函数嵌入——比如验证码场景，我在Excel的data里写 `dddd_ocr_text("{{image}}")`，渲染后eval会自动调用OCR函数识别验证码，把复杂逻辑也数据化了。"

### 11.3 优化点3：数据库断言与提取双通道

**面试话术：**

"很多接口自动化框架只做HTTP响应断言，但实际上接口返回成功不代表数据真的写对了——比如新增仓库接口返回code=200，但数据库里可能字段写错了、或者操作日志表没记录。只断言响应体会漏掉这类问题。

我在框架中加了**JDBC数据库断言和提取双通道**：断言方面，在Excel中增加了sql_check和sql_expected两列，支持单条SQL和多条SQL元组两种模式，单条用硬断言、多条用pytest.assume软断言逐条校验；提取方面，增加了sqlExData列，可以把SQL查询结果存入全局变量供后续用例使用。数据库操作统一封装在Database类里，用DictCursor返回字典、with上下文管理自动释放游标、自定义异常区分连接/查询/修改三类错误。

效益：第一，测试覆盖率从'接口层'提升到'接口+数据层'，能发现响应体断言发现不了的数据一致性问题；第二，数据库断言也数据驱动了，在Excel里写SQL就行，不需要为每个需要查库的用例写单独的Python代码；第三，Database类封装后，conftest里的数据清理从原来30多行硬编码pymysql连接缩减到一行 `Database().execute_sqls(SQL1,SQL2,SQL3,SQL4)`。"

### 11.4 优化点4：验证码OCR自动识别

**面试话术：**

"登录接口带图形验证码是自动化测试的经典难题——验证码就是为了防自动化的。常见的妥协方案是让开发在测试环境加万能验证码、或者临时关闭验证码，但这会导致测试环境和生产环境不一致，测出来的结果不可信。

我的解决方案是**集成ddddocr深度学习验证码识别**：验证码接口返回的是base64编码的图片，我写了一个dddd_ocr_text预处理函数，流程是base64去头→解码→PIL打开→转PNG字节流→ddddocr神经网络分类识别，最终返回验证码字符串。然后在Excel用例的data字段里直接写 `captcha: dddd_ocr_text("{{image}}")`，框架渲染时通过eval自动调用这个函数完成识别。

效益：第一，测试环境不需要任何特殊处理，和生产环境完全一致，测试结果真实可信；第二，登录场景全自动化，不需要人工介入输验证码，CI/CD流水线可以无人值守运行；第三，ddddocr是纯本地模型，不需要调用第三方OCR API，没有费用也没有数据外泄风险，识别速度在毫秒级。"

### 11.5 优化点5：多重断言软断言机制

**面试话术：**

"早期框架的多字段断言用的是普通assert，第一个字段失败就抛异常停了，后面的字段根本不校验——比如一个接口同时断言status_code、code、响应时间、字段类型，status_code断言失败了，你根本不知道code对不对、响应时间超没超，要改好一个再跑一次才能看到下一个问题，调试效率很低。

我把多字段断言全部改成了**pytest.assume软断言**：在base_assert.py的MainAssert里，每个原子断言方法的返回值都用pytest.assume()包裹，assume不会在失败时立即抛异常，而是记录失败信息继续执行，所有断言跑完后统一报告哪些失败了。多SQL断言也同样用assume。

效益：第一，一次执行就能暴露全部断言失败项，不需要反复跑用例逐个排查，调试效率提升明显——原来可能要跑3-4次才能定位全部问题，现在1次就够；第二，软断言只用于多字段场景，单字段场景仍然用硬assert快速失败，两种策略按需选择，不是一刀切；第三，失败信息完整，Allure报告里能看到每个断言字段的预期值和实际值，定位问题更快。"

### 11.6 优化点6：自定义异常体系

**面试话术：**

"早期数据库操作的异常处理是直接catch Exception然后打日志，所有错误混在一起——连接超时、SQL语法错、权限不足，全部都是'数据库出错了'，排查的时候要去翻日志堆栈才能知道到底是哪一步出的问题。

我定义了**三类自定义异常**：DatabaseException（连接失败）、GetDataException（查询失败）、ExecuteSqlException（增删改失败），都继承Exception并携带message和code。在Database类的三个方法（__get_connect、get_one、execute_sqls）中分别捕获原始异常，记录日志后抛出对应的自定义异常。

效益：第一，异常语义化，上层可以精准捕获特定类型做不同处理——比如连接失败可以加重试机制，查询失败直接记录用例失败；第二，排查问题时一眼就能看出是连接阶段还是执行阶段出错，不需要翻堆栈；第三，自定义异常携带错误码，后续接入告警系统时可以按错误码分级告警。"

### 11.7 效益量化总结

| 优化项 | 优化前 | 优化后 | 效益 |
|--------|--------|--------|------|
| 断言体系 | if-else硬编码，主流程30+行 | 策略模式，主流程1行 | 主流程代码缩减90%，新增断言类型不改旧代码 |

### 11.8 面试完整话术模板（3分钟版本）

"我做的这个接口自动化框架是基于pytest+requests+Allure的纯数据驱动框架，测试用例全部维护在Excel里，新增用例不需要改代码。

框架的核心执行流程是：run.py启动pytest → excel_utils读取Excel过滤出启用的用例 → parametrize参数化逐条执行 → 每条用例先经过Jinja2模板渲染把{{token}}这类全局变量替换成实际值 → case_analyse解析成requests可用的请求参数 → send_http_request发请求 → http_assert自动判断单/多断言策略执行 → jdbc_assert做数据库层校验 → extractor把需要传递的数据提取到全局变量字典供下一条用例使用 → 全部跑完后conftest的session级fixture自动清理测试数据。

我在框架中主要做了几个方面的优化：

第一是**断言体系的策略模式重构**。原来断言是写死在主流程里的if-else，我抽象出DataAssert基类和SingleAssert/MultipleAssert策略类，通过obj_processor工厂自动分发，主流程从几十行缩减到一行，新增断言类型不需要改旧代码。多字段断言用pytest.assume软断言，一次执行暴露全部问题。

第二是**用例间数据关联的Jinja2模板机制**。维护一个全局变量字典，用例提取的数据存进去，后续用例在Excel里写{{token}}就能引用，完全声明式，测试人员不需要懂编程。还支持在Excel里嵌入dddd_ocr_text函数调用，实现验证码自动识别。

第三是**HTTP+JDBC双断言通道**。不仅校验接口响应，还能直接查数据库校验数据落库正确性，单条SQL硬断言、多条SQL软断言，数据库操作统一封装在Database类里，带自定义异常体系。

这些优化带来的效益是：用例维护零代码，测试人员可独立编写；一次执行暴露全部断言问题，调试轮次减少；测试覆盖从接口层延伸到数据层；登录场景全自动化，CI/CD无人值守。框架目前覆盖了登录、商品中心、基础信息管理等模块，在CI流水线上稳定运行。"

## 十二、总结

本框架是一个**工程化程度较高的接口自动化测试框架**，核心特点可以概括为：

1. **纯数据驱动**：Excel维护用例，代码只做执行引擎，新增用例零代码
2. **策略模式断言**：单/多断言、单/多SQL断言自动识别分发，可扩展
3. **全局变量关联**：Jinja2模板渲染 + all字典，实现用例间动态数据传递
4. **双维度校验**：HTTP响应断言 + JDBC数据库断言，确保接口和数据双重正确
5. **全链路自动化**：验证码OCR识别、token自动传递、数据自动清理，无人值守
6. **完善的可观测性**：Allure可视化报告 + 双路日志 + 自定义异常，问题定位快

理解这个框架的关键是抓住**一条主线**（test_case的8步执行流程）和**两个核心机制**（Jinja2渲染的变量关联、策略模式的断言分发），其余模块都是围绕这两点做的支撑。
