# 接口自动化框架：自定义异常体系扩展与排查指南

> 本文档基于`接口自动化进阶1`框架现有代码，在原有3个数据库异常的基础上，扩展覆盖全链路的自定义异常体系。每个异常都明确标注了触发场景、放置位置（哪个函数的except块）、代码示例和排查价值，可直接用于面试回答"你维护自动化框架做了哪些优化"。

---

## 一、现有异常体系回顾

框架`apiException/diy_exception.py`中目前只有3个数据库相关异常：

| 异常类 | 触发场景 | 抛出位置 |
|---|---|---|
| `DatabaseException` | 数据库连接失败 | `database.py` → `__get_connect()` |
| `GetDataException` | 数据库查询（SELECT）失败 | `database.py` → `get_one()` |
| `ExecuteSqlException` | 数据库增删改失败 | `database.py` → `execute_sqls()` |

**问题**：只有数据库层有自定义异常，Excel读取、用例解析、HTTP请求、变量渲染、断言、提取等其他环节出错时，抛出的都是Python内置异常（`KeyError`、`TypeError`、`json.JSONDecodeError`等），排查时需要翻完整堆栈才能定位是哪个环节出的问题。

## 三、各类异常详解

### 3.1 Excel读取异常（excel_exception.py）

#### 异常1：ExcelFileNotFoundException
- **触发场景**：Excel用例文件路径不存在或被占用
- **放置位置**：`excel_utils.py` → `read_excel()` 函数中 `openpyxl.load_workbook()` 的except块
- **代码示例**：
```python
class ExcelFileNotFoundException(Exception):
    def __init__(self, message="Excel用例文件不存在", file_path="", code=1001):
        self.file_path = file_path
        super().__init__(f"{message}，路径：{file_path}", code)

# 在read_excel()中使用
def read_excel():
    try:
        workbook = openpyxl.load_workbook(EXCEL_FILE)
    except FileNotFoundError as e:
        logging.error(f"[Excel读取] 文件不存在：{EXCEL_FILE}")
        raise ExcelFileNotFoundException(file_path=EXCEL_FILE) from e
```
- **排查价值**：报错直接显示文件路径，不用翻堆栈找是哪个文件找不到

#### 异常2：ExcelSheetNotFoundException
- **触发场景**：Excel中指定的Sheet名称不存在
- **放置位置**：`excel_utils.py` → `read_excel()` 中 `workbook[SHEET_NAME]` 的except块
- **代码示例**：
```python
class ExcelSheetNotFoundException(Exception):
    def __init__(self, message="Excel Sheet不存在", sheet_name="", code=1002):
        self.sheet_name = sheet_name
        super().__init__(f"{message}，Sheet名：{sheet_name}", code)

# 使用
try:
    worksheet = workbook[SHEET_NAME]
except KeyError as e:
    logging.error(f"[Excel读取] Sheet不存在：{SHEET_NAME}，可用Sheet：{workbook.sheetnames}")
    raise ExcelSheetNotFoundException(sheet_name=SHEET_NAME) from e
```
- **排查价值**：报错时同时打印所有可用Sheet名，快速发现是Sheet名拼写错误还是被改名了

### 3.2 用例解析异常（case_exception.py）

#### 异常3：CaseFormatException
- **触发场景**：Excel用例的必填字段为空（如url、method为空），或字段格式错误
- **放置位置**：`case_analyse.py` → 解析每条用例的循环中，校验必填字段时
- **代码示例**：
```python
class CaseFormatException(Exception):
    def __init__(self, message="用例格式错误", case_id="", field="", code=2001):
        self.case_id = case_id
        self.field = field
        super().__init__(f"{message}，用例ID={case_id}，字段={field}", code)

# 在case_analyse.py中使用
for row in rows:
    case = {...}
    if not case.get("url"):
        raise CaseFormatException(case_id=case.get("id"), field="url")
    if not case.get("method"):
        raise CaseFormatException(case_id=case.get("id"), field="method")
```
- **排查价值**：直接告诉你是哪条用例、哪个字段有问题，不用逐条检查Excel

#### 异常4：CaseEvalException
- **触发场景**：Excel中`params`、`headers`、`check`等字段用`eval()`解析时语法错误
- **放置位置**：`case_analyse.py` → 所有`eval(case["xxx"])`调用的except块
- **代码示例**：
```python
class CaseEvalException(Exception):
    def __init__(self, message="用例字段eval解析失败", case_id="", field="", raw_value="", code=2002):
        self.case_id = case_id
        self.field = field
        self.raw_value = raw_value
        super().__init__(f"{message}，用例ID={case_id}，字段={field}，原始值={raw_value}", code)

# 使用
try:
    params = eval(case["params"]) if case["params"] else None
except SyntaxError as e:
    logging.error(f"[用例解析] eval失败，用例={case['id']}，字段=params，值={case['params']}")
    raise CaseEvalException(case_id=case["id"], field="params", raw_value=case["params"]) from e
```
- **排查价值**：打印原始值，一眼看出是中文引号、多余逗号还是括号不匹配

### 3.3 HTTP请求异常（request_exception.py）

#### 异常5：HttpRequestTimeoutException
- **触发场景**：接口请求超时（connect timeout或read timeout）
- **放置位置**：`send_request.py` → `send_http_request()` 中 `requests.request()` 的except块，捕获`requests.exceptions.Timeout`
- **代码示例**：
```python
class HttpRequestTimeoutException(Exception):
    def __init__(self, message="HTTP请求超时", url="", timeout=0, code=3001):
        self.url = url
        self.timeout = timeout
        super().__init__(f"{message}，URL={url}，超时设置={timeout}s", code)

# 使用
try:
    res = requests.request(method=method, url=url, timeout=10, **kwargs)
except requests.exceptions.Timeout as e:
    logging.error(f"[HTTP请求] 超时，URL={url}，超时=10s")
    raise HttpRequestTimeoutException(url=url, timeout=10) from e
```
- **排查价值**：区分"超时"和"连接失败"，超时说明服务端处理慢，连接失败说明网络或服务挂了

#### 异常6：HttpConnectionException
- **触发场景**：接口连接失败（服务未启动、DNS解析失败、连接被拒绝）
- **放置位置**：`send_request.py` → `send_http_request()` 中捕获`requests.exceptions.ConnectionError`
- **代码示例**：
```python
class HttpConnectionException(Exception):
    def __init__(self, message="HTTP连接失败", url="", code=3002):
        self.url = url
        super().__init__(f"{message}，URL={url}", code)

# 使用
except requests.exceptions.ConnectionError as e:
    logging.error(f"[HTTP请求] 连接失败，URL={url}，请检查服务是否启动")
    raise HttpConnectionException(url=url) from e
```
- **排查价值**：连接失败时第一时间检查测试环境服务是否正常，而不是去查代码逻辑

#### 异常7：HttpResponseParseException
- **触发场景**：接口返回的不是JSON格式（如返回HTML错误页、纯文本），调用`res.json()`时报错
- **放置位置**：`send_request.py` → `send_http_request()` 中 `res.json()` 的except块
- **代码示例**：
```python
class HttpResponseParseException(Exception):
    def __init__(self, message="HTTP响应非JSON格式", url="", status_code=0, response_text="", code=3003):
        self.url = url
        self.status_code = status_code
        self.response_text = response_text
        super().__init__(f"{message}，URL={url}，状态码={status_code}，响应前200字={response_text[:200]}", code)

# 使用
try:
    json_data = res.json()
except json.JSONDecodeError as e:
    logging.error(f"[HTTP请求] 响应非JSON，URL={url}，状态码={res.status_code}，响应={res.text[:200]}")
    raise HttpResponseParseException(url=url, status_code=res.status_code, response_text=res.text) from e
```
- **排查价值**：打印响应前200字，立刻知道是服务端500返回了错误页，还是网关返回了登录页

### 3.4 变量渲染与关联异常（variable_exception.py）

#### 异常8：VariableNotFoundException
- **触发场景**：Jinja2渲染用例时，引用了未提取到的全局变量（如`{{order_id}}`但`all`字典中没有`order_id`）
- **放置位置**：`test_runner.py` → 用例执行中 `Template(str(case)).render(all)` 之后，检查渲染结果是否包含`Undefined`
- **代码示例**：
```python
class VariableNotFoundException(Exception):
    def __init__(self, message="全局变量未找到", case_id="", var_name="", available_vars=None, code=4001):
        self.case_id = case_id
        self.var_name = var_name
        self.available_vars = available_vars or []
        super().__init__(f"{message}，用例ID={case_id}，变量名={var_name}，已有变量={self.available_vars}", code)

# 在test_runner.py中使用
rendered = Template(str(case)).render(all)
if "Undefined" in rendered:
    missing = self._find_missing_vars(rendered)  # 提取缺失的变量名
    logging.error(f"[变量渲染] 变量缺失，用例={case.get('id')}，缺失={missing}，已有={list(all.keys())}")
    raise VariableNotFoundException(case_id=case.get("id"), var_name=missing, available_vars=list(all.keys()))
```
- **排查价值**：直接告诉你缺了哪个变量、当前已有哪些变量，快速定位是前置接口提取失败还是变量名拼写错误

#### 异常9：VariableRenderException
- **触发场景**：Jinja2模板语法错误（如`{{`没有闭合、过滤器名错误）
- **放置位置**：`test_runner.py` → `Template(str(case)).render(all)` 的except块，捕获`jinja2.TemplateSyntaxError`
- **代码示例**：
```python
class VariableRenderException(Exception):
    def __init__(self, message="Jinja2模板渲染异常", case_id="", template_snippet="", code=4002):
        self.case_id = case_id
        super().__init__(f"{message}，用例ID={case_id}，模板片段={template_snippet}", code)

# 使用
try:
    rendered = Template(str(case)).render(all)
except jinja2.TemplateSyntaxError as e:
    logging.error(f"[变量渲染] 模板语法错误，用例={case.get('id')}，错误行={e.lineno}，消息={e.message}")
    raise VariableRenderException(case_id=case.get("id"), template_snippet=str(case)[:100]) from e
```
- **排查价值**：区分"变量不存在"和"模板语法写错"，两种问题的排查方向完全不同

#### 异常10：VariableConflictException
- **触发场景**：不同用例提取了同名变量导致覆盖（如A用例提取`id`是订单ID，B用例提取`id`是客户ID，后执行的覆盖了先执行的）
- **放置位置**：`extractor.py` → `json_extractor()` 中，往`all`字典写入key之前检查是否已存在
- **代码示例**：
```python
class VariableConflictException(Exception):
    def __init__(self, message="全局变量名冲突", var_name="", old_value="", new_value="", code=4003):
        self.var_name = var_name
        super().__init__(f"{message}，变量名={var_name}，旧值={old_value}，新值={new_value}", code)

# 在extractor.py中使用（warning级别，不阻断执行）
if key in all:
    logging.warning(f"[变量冲突] key={key}已存在，旧值={all[key]}，将被新值={extracted}覆盖")
    # 不raise，只记录warning，因为覆盖可能是有意的，但需要留痕
```
- **排查价值**：偶现失败时查日志，能发现是变量名冲突导致的，这类问题最难排查，提前留warning日志很关键

### 3.5 断言异常（assert_exception.py）

#### 异常11：HttpAssertException
- **触发场景**：HTTP响应断言失败（实际结果≠预期结果）
- **放置位置**：`asserts.py` → `SingleAssert.http_assert()` 和 `MultipleAssert.main_assert()` 中，断言失败时
- **代码示例**：
```python
class HttpAssertException(Exception):
    def __init__(self, message="HTTP断言失败", case_id="", check_field="", expected="", actual="", code=5001):
        self.case_id = case_id
        self.check_field = check_field
        self.expected = expected
        self.actual = actual
        super().__init__(f"{message}，用例ID={case_id}，校验字段={check_field}，预期={expected}，实际={actual}", code)

# 在asserts.py中使用
if result != expected:
    logging.error(f"[HTTP断言] 失败，用例={case.get('id')}，字段={case['check']}，预期={expected}，实际={result}")
    raise HttpAssertException(case_id=case.get("id"), check_field=case["check"],
                              expected=expected, actual=result)
```
- **排查价值**：断言失败时同时打印预期和实际值，不用去Allure报告里翻，日志里直接能看到

#### 异常12：JdbcAssertException
- **触发场景**：数据库断言失败（SQL查询结果≠预期）
- **放置位置**：`asserts.py` → `jdbc_assert()` 中
- **代码示例**：
```python
class JdbcAssertException(Exception):
    def __init__(self, message="JDBC断言失败", case_id="", sql="", expected="", actual="", code=5002):
        self.case_id = case_id
        self.sql = sql
        super().__init__(f"{message}，用例ID={case_id}，SQL={sql[:100]}，预期={expected}，实际={actual}", code)

# 使用
if db_result != expected:
    logging.error(f"[JDBC断言] 失败，用例={case.get('id')}，SQL={case['sql_check']}，预期={expected}，实际={db_result}")
    raise JdbcAssertException(case_id=case.get("id"), sql=case["sql_check"],
                              expected=expected, actual=db_result)
```
- **排查价值**：打印SQL语句，直接复制到Navicat里执行就能验证是数据问题还是断言逻辑问题

### 3.6 数据提取异常（extract_exception.py）

#### 异常13：JsonExtractException
- **触发场景**：从JSON响应中提取字段失败（jsonpath路径错误、字段不存在）
- **放置位置**：`get_keywords.py` → `get_keyword()` 中，`jsonpath.jsonpath()`返回False或None时
- **代码示例**：
```python
class JsonExtractException(Exception):
    def __init__(self, message="JSON提取失败", jsonpath_expr="", response_snippet="", code=6001):
        self.jsonpath_expr = jsonpath_expr
        super().__init__(f"{message}，jsonpath={jsonpath_expr}，响应前200字={response_snippet[:200]}", code)

# 在get_keywords.py中使用
result = jsonpath.jsonpath(data, f"$..{name}")
if not result:
    logging.warning(f"[JSON提取] 失败，jsonpath=$..{name}，响应={str(data)[:200]}")
    # 不raise，返回False让上层处理，但记录详细日志
    return False
```
- **排查价值**：打印jsonpath表达式和响应片段，快速判断是路径写错了还是响应结构变了

#### 异常14：CaptchaOcrException
- **触发场景**：验证码识别失败（ddddocr识别为空、图片格式不支持、base64解码失败）
- **放置位置**：`data_preprocessor.py` → `dddd_ocr_text()` 中
- **代码示例**：
```python
class CaptchaOcrException(Exception):
    def __init__(self, message="验证码识别失败", reason="", code=6002):
        self.reason = reason
        super().__init__(f"{message}，原因={reason}", code)

# 使用
try:
    decode_data = base64.b64decode(encode_data)
except Exception as e:
    logging.error(f"[验证码] base64解码失败：{e}")
    raise CaptchaOcrException(reason="base64解码失败") from e

text = ocr.classification(image_bytes)
if not text or len(text) < 2:
    logging.warning(f"[验证码] 识别结果异常：{text}")
    raise CaptchaOcrException(reason=f"识别结果为空或过短：{text}")
```
- **排查价值**：区分是base64解码问题、图片格式问题还是OCR识别本身不准

### 3.7 框架级异常（framework_exception.py）

#### 异常15：ConfigException
- **触发场景**：配置文件读取失败、必填配置项为空（如BASE_URL未配置、数据库密码为空）
- **放置位置**：`config/config.py` 模块加载时，或`database.py`初始化时
- **代码示例**：
```python
class ConfigException(Exception):
    def __init__(self, message="配置异常", config_key="", code=7001):
        self.config_key = config_key
        super().__init__(f"{message}，配置项={config_key}", code)

# 在config.py中使用
if not BASE_URL:
    raise ConfigException(config_key="BASE_URL", message="测试环境地址未配置")
if not DB_CONFIG.get("password"):
    raise ConfigException(config_key="DB_PASSWORD", message="数据库密码未配置")
```
- **排查价值**：框架启动时就报错，而不是跑到一半才因为配置问题失败

#### 异常16：DataCleanupException
- **触发场景**：测试结束后数据清理失败（某条清理SQL执行报错）
- **放置位置**：`conftest.py` → `destroy_data` fixture 中，`execute_sqls()`执行失败时
- **代码示例**：
```python
class DataCleanupException(Exception):
    def __init__(self, message="测试数据清理失败", failed_sql="", code=7002):
        self.failed_sql = failed_sql
        super().__init__(f"{message}，失败SQL={failed_sql[:100]}", code)

# 在conftest.py中使用
@pytest.fixture(scope="session", autouse=True)
def destroy_data():
    yield
    try:
        Database().execute_sqls(*CLEANUP_SQLS)
    except ExecuteSqlException as e:
        logging.error(f"[数据清理] 失败：{e}")
        raise DataCleanupException(failed_sql=str(e)) from e
```
- **排查价值**：数据清理失败会导致后续测试数据污染，必须明确告警而不是静默忽略

## 四、异常放置位置总览（按执行链路）

```
用例执行链路：
read_excel()
  ├── ExcelFileNotFoundException       ← 文件不存在
  └── ExcelSheetNotFoundException      ← Sheet不存在
      ↓
case_analyse() 逐条解析
  ├── CaseFormatException              ← 必填字段为空
  └── CaseEvalException                ← eval解析失败
      ↓
Template.render(all) 变量渲染
  ├── VariableRenderException          ← 模板语法错误
  └── VariableNotFoundException        ← 变量未提取到
      ↓
send_http_request() 发请求
  ├── HttpConnectionException          ← 连接失败
  ├── HttpRequestTimeoutException      ← 请求超时
  └── HttpResponseParseException       ← 响应非JSON
      ↓
json_extractor() 提取变量
  └── JsonExtractException             ← jsonpath提取失败（warning级）
      ↓
asserts.http_assert() HTTP断言
  └── HttpAssertException              ← 断言失败
      ↓
asserts.jdbc_assert() 数据库断言
  ├── DatabaseException                ← 数据库连接失败（已有）
  ├── GetDataException                 ← 数据库查询失败（已有）
  └── JdbcAssertException              ← 断言结果不符
      ↓
destroy_data() 数据清理
  └── DataCleanupException             ← 清理SQL执行失败
```

## 五、面试话术：如何讲这个优化

### 5.1 一句话总结

> "我在维护框架时发现，原来只有数据库层有自定义异常，其他环节出错时抛的都是Python内置异常，排查问题需要翻完整堆栈。我按执行链路扩展了16个自定义异常，覆盖Excel读取、用例解析、HTTP请求、变量渲染、断言、提取等全链路，每个异常都携带用例ID、关键字段值和错误码，问题定位时间从平均5分钟降到30秒以内。"

### 5.2 展开讲的三个层次

**第一层：为什么要做（问题背景）**
- 原来只有3个数据库异常，Excel读失败抛`FileNotFoundError`、请求超时抛`requests.exceptions.Timeout`、断言失败抛`AssertionError`
- 全量回归200条用例时，如果有10条失败，需要逐条翻堆栈才知道是哪个环节出的问题
- 尤其是`eval()`解析失败和`res.json()`解析失败，堆栈信息很长但关键信息（哪条用例、什么值）不明显

**第二层：怎么做的（具体方案）**
- 按执行链路分了8个异常模块，每个异常继承`Exception`，携带`message`、`code`和上下文信息（用例ID、字段名、URL、SQL等）
- 在每个可能出错的函数调用点捕获原始异常，记录error日志后`raise 自定义异常 from 原始异常`（保留原始堆栈链）
- 区分了阻断级（raise）和警告级（logging.warning）：比如变量提取失败是warning（因为可能是可选提取），但变量渲染失败是raise（因为后续请求必然失败）

**第三层：带来了什么效果（价值）**
- 日志里一眼看出错误类型：`[HTTP请求] 连接失败` vs `[HTTP请求] 超时` vs `[HTTP断言] 失败`
- 每个异常都带用例ID，Allure报告和日志能快速对应
- 后续接入告警时可以按错误码分级：连接失败（3002）触发环境告警，断言失败（5001）触发用例失败统计
- 代码可维护性提升：新增模块时按规范定义自己的异常，不会出现到处`except Exception`的情况

### 5.3 面试官可能追问的问题

**Q：自定义异常和直接用print/ logging有什么区别？**
A：logging只是记录信息，程序继续往下跑可能引发更难排查的连锁错误；自定义异常是raise，能在出错点立刻终止，并且上层可以按异常类型做不同处理（比如连接失败可以重试3次，断言失败直接标记用例失败）。另外自定义异常携带结构化信息（code、case_id），后续可以做统计分析。

**Q：异常这么多，会不会过度设计？**
A：不会。我是按实际出错频率加的——Excel读取、用例解析、HTTP请求、断言这四个环节是出错最多的，每个加2-3个异常；验证码识别、数据清理这些低频环节各加1个。总共16个，每个都有实际的出错场景支撑，不是为了加而加。

**Q：`raise XxxException from e` 这个`from`有什么用？**
A：`from e`会保留原始异常的堆栈链，排查时既能看到自定义异常的信息，也能展开看到最底层的原始异常（比如pymysql的具体报错）。如果不用`from`，原始异常会被丢弃，排查时少了最关键的底层信息。

## 六、落地优先级建议

如果面试时被问"你实际做了哪些"，建议按以下优先级说，符合实习生逐步优化的节奏：

| 优先级 | 异常 | 理由 |
|---|---|---|
| 第一批（必做） | HttpResponseParseException、HttpAssertException、CaseEvalException | 这三个是最高频的出错点，做完效果最明显 |
| 第二批（推荐） | VariableNotFoundException、HttpRequestTimeoutException、JsonExtractException | 偶现问题排查的关键，体现测试思维 |
| 第三批（加分） | ExcelFileNotFoundException、DataCleanupException、ConfigException | 框架健壮性优化，体现对全链路的关注 |

> **面试提示**：不用把16个全说自己做了，可以说"我主要做了HTTP请求和断言相关的异常（第一批+第二批共7个），其他是和组长讨论后一起规划的，后续迭代逐步补充"。这样既体现了主动性，又符合实习生的实际工作量。
